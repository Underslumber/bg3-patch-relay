# AGENTS.md

Инструкции для агентов, работающих в этом репозитории (Claude Code читает их через `CLAUDE.md`).

Мод для Baldur's Gate 3 — приватный слой патчей поверх чужих модов; что именно он патчит, перечислено в [README](README.md). Своего контента нет: только переопределения отдельных записей из статов и точечные серверные обработчики Script Extender.

В статах BG3 побеждает **последняя загруженная** запись с этим именем. Отсюда два правила, из которых следует всё остальное: мод обязан стоять ниже всех патчируемых модов в порядке загрузки, а сам патч — быть минимальным.

## Как писать патч

Только мягкое переопределение: `new entry` + `using` с тем же именем. Тогда наследуется чужая запись, загруженная раньше, и меняются лишь перечисленные `data`-строки.

```
new entry "BLADESONG"
type "StatusData"
data "StatusType" "BOOST"
using "BLADESONG"
data "Boosts" "…"
```

Без `using` запись создаётся с дефолтами и затирает чужую целиком — так делать только осознанно и с пометкой в файле патча.

Поле переопределяется **целиком**: если в патче есть `Boosts`, всё содержимое `Boosts` из чужого мода замещается, поэтому в патч копируются и те бусты, которые менять не собирались. Отсюда же главный риск апдейтов: правка апстрима внутри переопределённого поля до игрока не доедет.

Файлы статов именуются по файлу-источнику в патчируемом моде (`Status_BOOST.txt` — статусы типа BOOST, и т. д.).

Lua применяется только там, где мягкого переопределения статов недостаточно. Требования — в `Mods/…/ScriptExtender/Config.json`: BG3 Script Extender 29 и новее, таблица мода `BG3PatchRelay`. Переносить можно только реализацию, проверенную в отдельной установленной сборке: UUID хранилища меняется на UUID Patch Relay, тестовые имена и отладочные префиксы удаляются, а поведение фиксируется в файле патча. Новая логика не должна требовать изменения исходного мода.

Ограничения движка, которые уже стоили времени: `AC()` принимает только целое число (`ArmorClassBoostComponent.AC` — `int32`), выражение туда не подставить — отсюда лестницы из взаимоисключающих `IF(...)`. Ветки `IF` лучше делать взаимоисключающими, а не суммирующимися: тултип показывает каждый сработавший буст отдельной строкой.

## Обязательные спутники правки

Реестр патчей — смысл репозитория: без него через полгода неясно, какой апдейт чужого мода что ломает. Он живёт в двух местах сразу — строка в таблице README и полное описание в `docs/patches/<мод>-<тема>.md`.

README существует в двух локализациях: `README.md` (русский, основной) и `README.en.md` (английский). Таблицы в них зеркальные, поэтому строка добавляется, меняется и удаляется сразу в обоих файлах — иначе английская версия молча протухает. Файлы `docs/` остаются русскими, английский README ссылается на них как есть.

- Новый или изменённый патч — файл в `docs/patches/` по образцу `dnd55e-bladesong.md` (шапка-таблица с версией чужого мода, нашим файлом и файлом-источником, перечнем переопределённого и «Базисом», дальше «зачем» прозой) и строка в таблице патчей обоих README: ссылка, имя мода, одна фраза о том, что патч делает.
- Патч по новому чужому моду — ещё три дополнения: карточка мода в `docs/patched-mods.md` по образцу существующей, строка в таблице «Затронутые моды» / «Affected mods» обоих README и запись в `Dependencies` внутри `Mods/…/meta.lsx` (Folder, Name, UUID, PublishHandle, Version64).
- Апстрим починил вопрос сам — патч удаляется, файл описания остаётся, а его строка переезжает в таблицу «Снятые» / «Removed» обоих README.

## Сверка с апстримом

Откуда брать оригинал записи — в карточке мода в `docs/patched-mods.md`: там ссылка на репозиторий исходников, путь к локальной копии и зеркальный путь внутри неё. Найденную запись сравнивать с «Базисом» из файла патча в `docs/patches/`. Совпало — патч жив. Изменилось — патч переписывается под новую версию, а не остаётся как есть.

Заодно сверяется строка зависимости: `python scripts/sync-parent-meta.py --check` читает `meta.lsx` патчируемого мода из локальной копии (или с GitHub по `--parent-url`) и показывает расхождения в `Dependencies`; без `--check` он их применяет. Нужный блок ищется по UUID родителя, поэтому прочие `ModuleShortDesc` не задеваются. Обновлённая версия зависимости означает, что и «Версия на момент патча» в файлах `docs/patches/` устарела — эти две записи ходят парой.

## Команды

```powershell
./scripts/build-lslib.ps1              # собрать <Folder>.pak в корне репозитория
./scripts/build-lslib.ps1 -Install     # плюс скопировать в %LOCALAPPDATA%\Larian Studios\Baldur's Gate 3\Mods
./scripts/build-lslib.ps1 -Divine C:\path\to\Divine.exe   # явный путь к упаковщику
./scripts/build-lslib.ps1 -VersionTag v1.2.0              # версия сборки из тега
./scripts/build-lslib.ps1 -VersionTag v1.2.0 -WriteMeta   # и записать её в meta.lsx репозитория

./scripts/link-bg3-dev-folders.ps1     # подключить репозиторий к игре симлинками (для Toolkit)
./scripts/unlink-bg3-dev-folders.ps1   # снять подключение

python scripts/sync-parent-meta.py --check   # сверить Dependencies с meta.lsx патчируемого мода
python scripts/sync-parent-meta.py           # и обновить
```

Тестов нет — проверка только в игре.

Сборке нужны PowerShell 7 и `Divine.exe` из LSLib: путь берётся из `$env:BG3_DIVINE`, иначе из соседнего репозитория `../bg3-dnd55e-russian-localization/.tools/lslib/Packed/Tools/Divine.exe`. `-Install` отказывается работать при запущенной игре и делает бэкап прежнего `.pak` (`*.pak.bak-<таймштамп>`, оба игнорируются git).

`-VersionTag` разбирает `vX.Y.Z` или `vX.Y.Z-суффикс` в `ModuleInfo/Version64` — упакованный `int64` вида `major<<55 | minor<<47 | revision<<31 | build`; у предрелизного тега `build` считается как порядковый номер среди уже существующих `vX.Y.Z-*`. По умолчанию версия подставляется только в сборку, а `meta.lsx` в репозитории не меняется: сборка из тега воспроизводима, но версия в git не уезжает незаметно. Записать её в репозиторий — явным `-WriteMeta`.

Пакуются только `Mods/` и `Public/`: Divine всегда получает staging-копию этих двух каталогов, поэтому документация, скрипты и прежний `.pak` в игру не уезжают. Обрубок вместо пакета Divine изредка выдаёт молча, с нулевым кодом возврата, — сборка отбрасывает результат меньше килобайта и повторяет со второй staging-копии, рядом с репозиторием (`build-staging`, игнорируется git): на другом корне попытка обычно проходит. Имя каталога не начинается с точки не случайно — из пути с таким сегментом Divine не берёт ни одного файла и молча отдаёт пустой пакет в 48 байт.

Имя скрипта называет тип сборки: `build-<инструмент>.ps1`. Сборка официальным Toolkit станет отдельным `build-toolkit.ps1` рядом, а не флагом внутри существующего — у способов разные требования к окружению и разный результат. Скриптам место в `scripts/`, корень остаётся под игровые ветки и документацию.

`link-bg3-dev-folders.ps1` заводит симлинки из репозитория в `Data\` игры — так Toolkit видит мод как свой проект, а правки идут по-прежнему в репозиторий. Линкуются `Mods`, `Public`, `Editor\Mods` и `Projects`; первые два обязательны, остальные пропускаются, если каталога нет. Игра ищется через реестр Steam и `libraryfolders.vdf`; нужны права на симлинки (режим разработчика Windows). Пока линки стоят, игра берёт мод из репозитория, а не из установленного `.pak`, — две копии одновременно смысла не имеют.

## Toolkit

Мод заведён как проект официального Toolkit и через эти симлинки работает прямо с репозиторием. Из этого следуют правила, каждое куплено ошибкой.

**Только ASCII в `meta.lsx`.** Тулкит читает файл как cp1251, а пишет UTF-8, поэтому любой символ вне ASCII портится при каждой публикации и уезжает в игру: `—` в имени мода превратилось в «вЂ”» и так и показалось в списке модов. Тире, кавычки-ёлочки, кириллица в `Name`, `Description`, `Author` — исключены; русский текст живёт в документации, а не в манифесте.

**`meta.lsx` принадлежит тулкиту.** Публикация переписывает его целиком: `Version64`, `FileSize` и `MD5` пакета, пустой `Conflicts`, `PublishHandle`, узел `Scripts` со стандартными UUID; `TargetModes` удаляется. У соседних модов манифест выглядит так же. Ручные правки переживут только то, чего тулкит не трогает; всё остальное восстанавливать бессмысленно.

**`Dependencies` тулкит заполняет по установленному моду, а не по апстриму.** После публикации там оказалась версия пака из папки модов игры (4.11.21.11), тогда как исходники апстрима были на 4.11.22.3. Это не ошибка: зависимость описывает то, с чем мод собран и проверен. Поэтому `sync-parent-meta.py` правит манифест только когда публикация идёт мимо тулкита; при обычном цикле его роль — `--check`, чтобы видеть, насколько отстала проверенная связка.

**Toolkit кладёт пакет как `<Folder>.pak`** — `PatchRelay_146ee64d-….pak`. `build-lslib.ps1` использует то же имя: под разными именами обе сборки лежали бы в папке модов одновременно.

`GUI/metadata.lsf` внутри `Mods/…` создан тулкитом и коммитится вместе с остальным — он попадает в пакет.

Окончания строк зафиксированы в `.gitattributes`: `.lsx` — LF (так пишет тулкит), стат-файлы — CRLF (так приходят из апстрима). Без этого `core.autocrlf=true` переписывает файлы на каждой публикации и топит настоящие правки в шуме.

## Проверка и целевой объект

**Доказательство одно — поведение в игре.** Собранный `.pak`, чистая консоль Script Extender и сработавший `print` в Lua говорят, что запись прочитана, тултип — что победила наша; во что буст превратился на листе персонажа, не показывает ни то ни другое. Пока эффект не увиден в игре в том виде, ради которого патч писался, патч — гипотеза.

**Целевой объект называется до сборки, проверки и коммита.** Репозиторий через симлинки и установленный `.pak` — разные моды, и `-Install` симлинки не снимает: пока они стоят, свежий пакет в папке модов не проверяется вовсе. У патчируемого мода объектов тоже несколько — источник из карточки в `docs/patched-mods.md`, локальная копия, установленный пакет, — и «Версия на момент патча» описывает тот, по которому патч действительно сверен. «Проверено» без ответа на вопрос «где именно» не значит ничего.

**Гипотеза не переезжает в документацию как факт.** В «Базис» идёт прочитанное в источнике, в таблицу README — то, что патч делает на самом деле; догадка о причине игрового поведения помечается догадкой. Текст коммита пишется после заморозки правки и по фактическому `git diff`: только вошедшие в него изменения и только выполненные проверки.

**Сначала скучная причина.** Объяснение через особенность движка берётся после того, как отброшены обычные: мод стоит не ниже патчируемого, имя записи разошлось с оригиналом, `using` потерян и запись собралась с дефолтов, переопределённое поле затёрло чужие строки целиком, игра читает не тот объект, пакет не пересобран или Divine отдал обрубок. Каждая выглядит как «баг игры» и проверяется за минуту.

**Опровергнутая посылка останавливает линию правок.** Проверка в игре не дала эффекта или пользователь опроверг предпосылку — не надстраивать следующий вариант поверх той же модели: отметить посылку как отвергнутую, перечислить выводы, которые на ней держались, и перечитать оригинал записи заново. После двух неудачных попыток причина ищется с чистого состояния — снять симлинки, воспроизвести исходное поведение без Patch Relay, и только потом чинить.

После сжатия контекста называются заново задача, целевой объект, доказанное игрой и отвергнутое. Иначе отвергнутая гипотеза возвращается как рабочая.

## Язык

Документация, комментарии и сообщения коммитов — по-русски; имена файлов, записей статов и полей — как в игре.
