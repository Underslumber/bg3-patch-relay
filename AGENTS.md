# AGENTS.md

Инструкции для агентов, работающих в этом репозитории (Claude Code читает их через `CLAUDE.md`).

## Что это за репозиторий

Мод для Baldur's Gate 3 — приватный слой патчей поверх чужих модов. Своего контента нет: только переопределения отдельных записей из статов других модов. Игровой код здесь — текстовые файлы статов и один XML-манифест; сборка — упаковка двух каталогов в `.pak`.

Ключевое следствие для любой правки: в статах BG3 побеждает **последняя загруженная** запись с этим именем, поэтому мод обязан стоять ниже всех патчируемых модов в порядке загрузки, а сам патч — быть минимальным.

## Команды

```powershell
./scripts/build-lslib.ps1              # собрать PatchRelay.pak в корне репозитория
./scripts/build-lslib.ps1 -Install     # плюс скопировать в %LOCALAPPDATA%\Larian Studios\Baldur's Gate 3\Mods
./scripts/build-lslib.ps1 -Divine C:\path\to\Divine.exe   # явный путь к упаковщику
```

Имя скрипта называет тип сборки: `build-<инструмент>.ps1`. Сейчас есть только `build-lslib.ps1` (Divine.exe из LSLib, игра для него не нужна); сборка официальным Toolkit от Larian, когда до неё дойдут руки, станет отдельным `build-toolkit.ps1` рядом, а не флагом внутри существующего — у способов разные требования к окружению и разный результат.

Тестов нет — проверка только в игре. `scripts/build-lslib.ps1` требует PowerShell 7 и `Divine.exe` из LSLib: путь берётся из `$env:BG3_DIVINE`, иначе из соседнего репозитория `../bg3-dnd55e-russian-localization/.tools/lslib/Packed/Tools/Divine.exe`. `-Install` отказывается работать при запущенной игре и делает бэкап прежнего `.pak` (`*.pak.bak-<таймштамп>`, оба игнорируются git).

Пакуются только `Mods/` и `Public/` — остальные файлы репозитория в `.pak` не попадают. Скриптам место в `scripts/`, а не в корне: корень остаётся под игровые ветки и документацию.

## Структура

```
Mods/PatchRelay_146ee64d-…/meta.lsx                       идентичность мода + Dependencies
Public/PatchRelay_146ee64d-…/Stats/Generated/Data/*.txt   собственно патчи
scripts/build-lslib.ps1                                   сборка .pak через LSLib + установка в игру
PATCHES.md                                                реестр: что, где, зачем, на какой версии
```

UUID мода `146ee64d-4202-44ea-bd9a-87fbcc4aa36e`; каталог `PatchRelay_146ee64d-4202-44ea-bd9a-87fbcc4aa36e` одинаков в обеих ветках, и `scripts/build-lslib.ps1` зашит на это имя — переименование ломает сборку.

Файлы статов именуются по файлу-источнику в патчируемом моде (`Status_BOOST.txt` — статусы типа BOOST, и т. д.).

## Как писать патч

Только мягкое переопределение: `new entry` + `using` с тем же именем. Тогда наследуется чужая запись, загруженная раньше, и меняются лишь перечисленные `data`-строки.

```
new entry "BLADESONG"
type "StatusData"
data "StatusType" "BOOST"
using "BLADESONG"
data "Boosts" "…"
```

Без `using` запись создаётся с дефолтами и затирает чужую целиком — так делать только осознанно и с пометкой в `PATCHES.md`.

Поле переопределяется **целиком**: если в патче есть `Boosts`, всё содержимое `Boosts` из чужого мода замещается, поэтому в патч копируются и те бусты, которые менять не собирались. Отсюда же главный риск апдейтов: правка апстрима внутри переопределённого поля до игрока не доедет.

Ограничения движка, которые уже стоили времени: `AC()` принимает только целое число (`ArmorClassBoostComponent.AC` — `int32`), выражение туда не подставить — отсюда лестницы из взаимоисключающих `IF(...)`. Ветки `IF` лучше делать взаимоисключающими, а не суммирующимися: тултип показывает каждый сработавший буст отдельной строкой.

## Обязательные спутники правки

- Новый или изменённый патч — подраздел в `PATCHES.md` внутри раздела своего мода (версия на момент патча, файл, запись, что именно переопределено, колонка «Базис» с исходным содержимым, и «зачем»). Реестр — смысл репозитория: без него через полгода неясно, какой апдейт чужого мода что ломает.
- Патч по новому чужому моду — сразу два дополнения: раздел мода в `PATCHES.md` с шапкой (UUID, Folder, PublishHandle, ссылка на исходники и путь к локальной копии) и запись в `Dependencies` внутри `Mods/…/meta.lsx` (Folder, Name, UUID, PublishHandle, Version64).
- Апстрим починил вопрос сам — патч удаляется, подраздел переезжает в раздел «Снятые» с сохранением группировки по моду.

## Сверка с апстримом

Откуда брать оригинал записи — записано в шапке раздела мода в `PATCHES.md`: там ссылка на репозиторий исходников, путь к локальной копии и зеркальный путь внутри неё. Для единственного пока патчируемого мода, DnD 5.5e All-in-One BEYOND, это `../bg3dnd` (форк [Underslumber/bg3dnd](https://github.com/Underslumber/bg3dnd), апстрим [Yoonmoonsik/bg3dnd](https://github.com/Yoonmoonsik/bg3dnd)), путь `Public/DnD2024_…/Stats/Generated/Data/`. Найденную запись сравнивать с колонкой «Базис».

Совпало — патч жив. Изменилось — патч переписывается под новую версию, а не остаётся как есть.
