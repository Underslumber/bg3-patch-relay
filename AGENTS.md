# AGENTS.md

Инструкции для агентов, работающих в этом репозитории (Claude Code читает их через `CLAUDE.md`).

## Что это за репозиторий

Мод для Baldur's Gate 3 — приватный слой патчей поверх чужих модов. Своего контента нет: только переопределения отдельных записей из статов и точечные серверные обработчики Script Extender. Игровой код здесь — текстовые файлы статов, Lua и один XML-манифест; сборка — упаковка двух каталогов в `.pak`.

Ключевое следствие для любой правки: в статах BG3 побеждает **последняя загруженная** запись с этим именем, поэтому мод обязан стоять ниже всех патчируемых модов в порядке загрузки, а сам патч — быть минимальным.

## Команды

```powershell
./scripts/build-lslib.ps1              # собрать <Folder>.pak в корне репозитория
./scripts/build-lslib.ps1 -Install     # плюс скопировать в %LOCALAPPDATA%\Larian Studios\Baldur's Gate 3\Mods
./scripts/build-lslib.ps1 -Divine C:\path\to\Divine.exe   # явный путь к упаковщику
./scripts/build-lslib.ps1 -VersionTag v1.2.0              # версия сборки из тега
./scripts/build-lslib.ps1 -VersionTag v1.2.0 -WriteMeta   # и записать её в meta.lsx репозитория

./scripts/link-bg3-dev-folders.ps1     # подключить репозиторий к игре симлинками (для Toolkit)
./scripts/unlink-bg3-dev-folders.ps1   # снять подключение

python scripts/sync-parent-meta.py --check   # сверить Dependencies с meta.lsx патчируемого мода
python scripts/sync-parent-meta.py           # и обновить
```

Имя скрипта называет тип сборки: `build-<инструмент>.ps1`. Сейчас есть только `build-lslib.ps1` (Divine.exe из LSLib, игра для него не нужна); сборка официальным Toolkit от Larian, когда до неё дойдут руки, станет отдельным `build-toolkit.ps1` рядом, а не флагом внутри существующего — у способов разные требования к окружению и разный результат.

Тестов нет — проверка только в игре. `scripts/build-lslib.ps1` требует PowerShell 7 и `Divine.exe` из LSLib: путь берётся из `$env:BG3_DIVINE`, иначе из соседнего репозитория `../bg3-dnd55e-russian-localization/.tools/lslib/Packed/Tools/Divine.exe`. `-Install` отказывается работать при запущенной игре и делает бэкап прежнего `.pak` (`*.pak.bak-<таймштамп>`, оба игнорируются git).

Пакуются только `Mods/` и `Public/` — остальные файлы репозитория в `.pak` не попадают. Скриптам место в `scripts/`, а не в корне: корень остаётся под игровые ветки и документацию.

`-VersionTag` разбирает тег `vX.Y.Z` в `ModuleInfo/Version64` — упакованный `int64` вида `major<<55 | minor<<47 | revision<<31 | build`. По умолчанию версия подставляется только в сборку, а `meta.lsx` в репозитории не меняется: сборка из тега воспроизводима, но версия в git не уезжает незаметно. Записать её в репозиторий — явным `-WriteMeta`. Divine изредка молча выдаёт обрубок вместо пакета, поэтому сборка отбрасывает результат меньше килобайта и повторяет с другого корня.

`link-bg3-dev-folders.ps1` заводит симлинки из репозитория в `Data\` игры — так Toolkit видит мод как свой проект, а правки идут по-прежнему в репозиторий. `Mods` и `Public` обязательны, `Editor\Mods` и `Projects` линкуются, только когда появятся: до заведения мода в тулките их просто нет. Игра находится через реестр Steam и `libraryfolders.vdf`; нужны права на симлинки (режим разработчика Windows). Помнить, что мод из `Data\Mods` игра берёт из репозитория, а не из установленного `.pak`, — две копии одновременно смысла не имеют.

## Toolkit

Мод заведён как проект официального Toolkit: `link-bg3-dev-folders.ps1` подключает `Mods`, `Public`, `Editor\Mods` и `Projects` симлинками, тулкит работает прямо с репозиторием. Из этого следуют правила, каждое куплено ошибкой.

**Только ASCII в `meta.lsx`.** Тулкит читает файл как cp1251, а пишет UTF-8, поэтому любой символ вне ASCII портится при каждой публикации и уезжает в игру: `—` в имени мода превратилось в «вЂ”» и так и показалось в списке модов. Тире, кавычки-ёлочки, кириллица в `Name`, `Description`, `Author` — исключены; русский текст живёт в документации, а не в манифесте.

**`meta.lsx` принадлежит тулкиту.** Публикация переписывает его целиком: инкрементирует `ModuleInfo/Version64`, проставляет `FileSize` и `MD5` собранного пакета, заводит пустой `Conflicts`, `PublishHandle` (ноль, пока мод не опубликован в mod.io) и узел `Scripts` с двумя стандартными UUID, а `TargetModes` удаляет — у соседних модов (`bg3dnd`, локализация) манифест выглядит так же. Ручные правки переживут только то, чего тулкит не трогает; всё остальное восстанавливать бессмысленно.

**`Dependencies` тулкит заполняет по установленному моду, а не по апстриму.** После публикации там оказалась версия пака из папки модов игры (4.11.21.11), тогда как исходники апстрима были на 4.11.22.3. Это не ошибка: зависимость описывает то, с чем мод собран и проверен. `sync-parent-meta.py` поэтому применяется к манифесту только когда публикация идёт мимо тулкита; при обычном цикле его роль — `--check`, чтобы видеть, насколько отстала проверенная связка.

**Toolkit кладёт пакет как `<Folder>.pak`** — `PatchRelay_146ee64d-….pak`. `build-lslib.ps1` использует то же имя: под разными именами обе сборки лежали бы в папке модов одновременно.

`GUI/metadata.lsf` внутри `Mods/…` создан тулкитом и коммитится вместе с остальным — он попадает в пакет.

Окончания строк зафиксированы в `.gitattributes`: `.lsx` — LF (так пишет тулкит), стат-файлы — CRLF (так приходят из апстрима). Без этого `core.autocrlf=true` переписывает файлы на каждой публикации и топит настоящие правки в шуме.

UUID мода `146ee64d-4202-44ea-bd9a-87fbcc4aa36e`; каталог `PatchRelay_146ee64d-4202-44ea-bd9a-87fbcc4aa36e` одинаков в обеих ветках, и `scripts/build-lslib.ps1` зашит на это имя — переименование ломает сборку.

Файлы статов именуются по файлу-источнику в патчируемом моде (`Status_BOOST.txt` — статусы типа BOOST, и т. д.).

## Как писать патч

Только мягкое переопределение: `new entry` + `using` с тем же именем. Тогда наследуется чужая запись, загруженная раньше, и меняются лишь перечисленные `data`-строки.

```
new entry "BLADESONG"
type "StatusData"
data "StatusType" "BOOST"
using "BLADESONG"
data "Boosts" "…"
```

Без `using` запись создаётся с дефолтами и затирает чужую целиком — так делать только осознанно и с пометкой в файле патча.

Поле переопределяется **целиком**: если в патче есть `Boosts`, всё содержимое `Boosts` из чужого мода замещается, поэтому в патч копируются и те бусты, которые менять не собирались. Отсюда же главный риск апдейтов: правка апстрима внутри переопределённого поля до игрока не доедет.

Lua применяется только там, где мягкого переопределения статов недостаточно; обработчики требуют BG3 Script Extender 29 и новее (`Mods/…/ScriptExtender/Config.json`). Переносить можно только реализацию, проверенную в отдельной установленной сборке: UUID хранилища меняется на UUID Patch Relay, тестовые имена и отладочные префиксы удаляются, а поведение фиксируется в файле патча. Новая логика не должна требовать изменения исходного мода.

Ограничения движка, которые уже стоили времени: `AC()` принимает только целое число (`ArmorClassBoostComponent.AC` — `int32`), выражение туда не подставить — отсюда лестницы из взаимоисключающих `IF(...)`. Ветки `IF` лучше делать взаимоисключающими, а не суммирующимися: тултип показывает каждый сработавший буст отдельной строкой.

## Обязательные спутники правки

Реестр патчей — смысл репозитория: без него через полгода неясно, какой апдейт чужого мода что ломает. Он живёт в двух местах: строка-оглавление в таблице `README.md` и полное описание в `docs/patches/<мод>-<тема>.md` (`dnd55e-bladesong.md`). Одно без другого не бывает.

- Новый или изменённый патч — файл в `docs/patches/` и строка в таблице README. В файле шапка-таблица (мод со ссылкой на `docs/patched-mods.md`, версия чужого мода на момент патча, наши файлы и файл-источник, что именно переопределено, «Базис» с исходным содержимым) и дальше «зачем» прозой. В таблице README — ссылка, имя мода и одна фраза о том, что патч делает.
- Патч по новому чужому моду — ещё три дополнения: раздел мода в `docs/patched-mods.md` (UUID, Folder, PublishHandle, страница мода, ссылка на исходники, путь к локальной копии и зеркальный путь внутри неё), строка в таблице «Затронутые моды» в README (внешние ссылки: mod.io, GitHub) и запись в `Dependencies` внутри `Mods/…/meta.lsx` (Folder, Name, UUID, PublishHandle, Version64).
- Апстрим починил вопрос сам — патч удаляется, файл описания остаётся, а его строка переезжает в таблицу «Снятые» в README.

## Сверка с апстримом

Откуда брать оригинал записи — записано в разделе мода в `docs/patched-mods.md`: там ссылка на репозиторий исходников, путь к локальной копии и зеркальный путь внутри неё. Для единственного пока патчируемого мода, DnD 5.5e All-in-One BEYOND, это `../bg3dnd` (форк [Underslumber/bg3dnd](https://github.com/Underslumber/bg3dnd), апстрим [Yoonmoonsik/bg3dnd](https://github.com/Yoonmoonsik/bg3dnd)), путь `Public/DnD2024_…/Stats/Generated/Data/`. Найденную запись сравнивать с «Базисом» из файла патча в `docs/patches/`.

Совпало — патч жив. Изменилось — патч переписывается под новую версию, а не остаётся как есть.

Заодно сверяется строка зависимости: `python scripts/sync-parent-meta.py --check` читает `meta.lsx` патчируемого мода из локальной копии (или с GitHub по `--parent-url`) и показывает расхождения в `Dependencies`; без `--check` он их применяет. Нужный блок ищется по UUID родителя, поэтому прочие `ModuleShortDesc` не задеваются. Обновлённая версия зависимости означает, что и «Версия на момент патча» в файлах `docs/patches/` устарела — эти две записи ходят парой.

## Язык

Документация, комментарии и сообщения коммитов — по-русски; имена файлов, записей статов и полей — как в игре.
